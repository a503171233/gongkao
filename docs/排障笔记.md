# 排障笔记（TROUBLESHOOTING）

> 更新：2026-09-03 · 按"症状 → 根因 → 解决"记录本次开发踩过的真实坑
> 新坑请追加到对应分类，不要覆盖旧记录。

## 一、部署类

### 1. 改了代码，线上没生效（最常见！）
**症状**：本地测试全过、文件已上传服务器，但 `curl` 接口还是旧行为（如 404、无新字段）。
**根因**：`api.py`/`index.html` 是 **COPY 进 Docker 镜像**的。上传宿主机文件 ≠ 容器内生效，只 `docker compose up -d` 不会重建镜像（compose 认为配置没变，复用旧容器）。
**解决**：
```bash
cd /home/ubuntu/gongkao
docker compose build backend frontend    # 缓存模式（只重做 COPY 层，几秒）
docker compose up -d backend frontend
```
**预防**：部署脚本里 build + up 成对执行；验证用 `docker exec gongkao-backend grep xxx /app/poc/api.py` 确认容器内文件已更新。

### 2. docker compose build --no-cache 卡死
**症状**：`pip install` 阶段长时间无进展（曾 20+ 分钟），HF 下载也慢。
**根因**：全量重装所有 pip 依赖 + 重新拉模型。
**解决**：永远用缓存模式 `docker compose build`（不加 --no-cache）。新增 pip 依赖时慎用，必要时单独 `pip install` 进容器测试。

### 3. nginx 502/504
**症状**：SSE 提问 502（网关错误）或 504（超时）。
**根因**：`proxy_read_timeout` 默认 60s，LLM 生成最慢实测 **121s**，超时被 nginx 掐断。
**解决**：nginx.conf 的 `/api/ask` location 已设 `proxy_read_timeout 300s`。若再遇，查 `docker logs gongkao-backend` 确认是 LLM 慢还是中转站 503。

## 二、模型 / 中转站类

### 4. 中转站模型 503
**症状**：`deepseek-chat`、`bge-m3` 等调用 503。
**根因**：中转站 ai.anyyds.cn 部分模型不可用/无该通道（21 个模型中仅 `gpt-5.6-luna` 稳定）。
**解决**：LLM 用 `gpt-5.6-luna`；Embedding 用本地 fastembed（`EMBED_PROVIDER=local`，bge-small-zh-v1.5），因为中转站无 embedding 通道。
**排查**：`docker exec gongkao-backend python -c "import os,urllib.request,json; ..."` 列模型列表。

### 5. HF 拉模型 401/失败
**症状**：首次启动拉 bge-small-zh ONNX 模型失败（401 或连不上）。
**根因**：HuggingFace 新式 xet CAS 存储绕过镜像直连官方。
**解决**：compose 已配 `HF_HUB_DISABLE_XET=1` + `HF_ENDPOINT=https://hf-mirror.com` + `HF_HUB_DISABLE_TELEMETRY=1`。模型缓存落 `/data/models` 挂载卷，不随容器销毁。

## 三、数据类

### 6. 用户/会话数据"消失"（P0，已修）
**症状**：重建 backend 容器后，注册的用户、会话历史全没了。
**根因**：`auth.py`/`chat.py` 默认库路径是相对路径（`data/auth.db`），容器内落在可写层 `/app/data/`，**容器重建即丢**（不在挂载卷）。
**解决**（已修复并验证 7/7 PASS）：
- `docker-compose.yml` 钉死 `AUTH_DB=/data/auth.db`、`CHAT_DB=/data/chat.db`
- `auth.py` 默认路径改为 `Config.data_dir / "auth.db"`（尊重 DATA_DIR=/data）
- 登录用户会话绑定其 `user_id`（匿名仍为 `anonymous`）
- **验证方法**：注册 → `docker compose restart backend` → 再登录，账号仍在。

## 四、Gitee OAuth 类

### 7. login 返回 307 而不是 302
**症状**：验证脚本断言 `302` 失败，实际 `curl -w '%{http_code}'` 返回 307。
**根因**：FastAPI `RedirectResponse` 默认 status_code=307（Temporary Redirect），307 才是标准行为，不是故障。
**解决**：断言改成 `307` 或检查 `Location` 头（重点看 client_id 和 redirect_uri 是否对）。
**教训**：验证脚本的断言要匹配框架真实行为，别想当然。

### 8. Gitee 授权页 redirect_uri 不合法
**症状**：用户点击 Gitee 登录，Gitee 页面报"回调地址不合法"。
**根因**：Gitee 后台创建应用时填的回调地址 ≠ 服务器 `.env` 的 `GITEE_REDIRECT_URI`（或端口/路径不一致）。
**解决**：两边都必须为 `http://YOUR_SERVER_IP:3000/api/auth/gitee/callback`。改任一侧后：Gitee 后台保存 / 服务器 `.env` 改完重建容器。

### 9. 回调 400 "state 无效或已过期"
**症状**：授权成功后回调报 400。
**根因**：`state` 在内存 dict（进程内），容器重启后旧 state 全失效；或超过 10 分钟 TTL。
**解决**：重新发起登录（state 每次随机生成，一次性）。若频繁出现且排除人为慢操作，考虑把 state 落到 Redis/DB（当前单进程内存够用）。

## 五、前端类

### 10. 前端修改后页面报错/功能没了
**症状**：改 index.html 后 div 错位、JS 函数 undefined、按钮不响应。
**根因**：手改 HTML 时 `div` 不配对 / `id` 重复 / 误删既有锚点。
**解决**：上线前跑 `docs/测试清单.md §三` 的结构检查脚本（div 配对、id 唯一、关键函数存在）。改完本地 `Ctrl+F5` 强刷缓存。

### 11. PowerShell curl 输出判断误报
**症状**：PowerShell 里 `$html = curl.exe ...; $html.Contains('xxx')` 全返回 False，但页面明明有。
**根因**：curl.exe 多行输出赋给变量是**字符串数组**，`.Contains()` 做整行相等而非子串匹配。
**解决**：用 `curl.exe ... | Out-String` 再 `.Contains()`，或 `Select-String -Pattern 'xxx' -Quiet`。

## 六、幻觉检测类

### 12. 编造查询没被拦截（中文数字绕过）
**症状**：编造"正确率高达百分之九十九点七"没触发拦截，但"99.7%"会拦。
**根因**：`guard.py` 数字校验只匹配阿拉伯数字（`\d+`），中文数字漏网。
**解决**（已修）：`_cn_nums()` 提取中文数字（含"百分之"前缀），`_cn_to_arabic()` 转阿拉伯形比对；`_check_facts` 同时校验两类。
**测试**：`test_guard.py` 含中文数字用例（selftest 下超纲反查跳过，数字校验独立生效）。

### 13. selftest 模式下超纲反查误杀
**症状**：本地 selftest 跑 guard 测试，超纲用例被拦/放行与预期不符。
**根因**：selftest 用哈希向量无语义，超纲反查必然误判。
**解决**（已定契约）：`EMBED_PROVIDER=selftest` 时超纲反查**跳过**（放行），线上 local embedding 才启用。测试断言按此契约写。

## 七、监控类

### 14. /api/metrics 404（或返回 HTML）
**症状**：`curl /guard/stats` 或 `/metrics` 返回前端 HTML 而非 JSON。
**根因**：nginx 只代理 `/api/` 前缀（`location /api/`），漏写 `/api` 的 URL 会落到静态页。
**解决**：所有后端接口一律用 `/api/...` 前缀访问（nginx 剥前缀转后端）。后端路由本身不带 `/api`（如 `/metrics`、`/guard/stats`、`/auth/gitee/*`）。

## 八、通用排查套路

1. **先看容器内文件**：`docker exec gongkao-backend grep '关键词' /app/poc/api.py` —— 确认代码真的在容器里（排除上传/重建遗漏）
2. **看后端日志**：`docker logs -f gongkao-backend`（SSE/守卫/错误都会打）
3. **隔离层验证**：curl 直打 `http://localhost:3000/api/xxx`（走 nginx 全链路）→ 不行再 `docker exec` 内直接 uvicorn 直连 9000 端口排除 nginx
4. **数据卷确认**：`docker exec gongkao-backend ls -la /data` —— auth.db/chat.db/vector 是否落卷
5. **改.env 后**：确认 `docker exec gongkao-backend env | grep GITEE` 能看到新值（env 注入容器）

## 九、2026-09-04 线上验收新坑

### 15. 后台登录报「CSRF: Origin 校验失败」
**症状**：admin.html 登录点提交即 403，但 curl（无 Origin）正常。
**根因**：前端 POST 带 `Origin: http://host:3000`（含端口），nginx `proxy_set_header Host $host` 把 Host 透传为**无端口** `host` → 后端 CSRF 中间件比较 `urlparse(origin).netloc == host` 不等 → 403。
**解决**（已修）：nginx.conf 三处 `proxy_set_header Host $host;` 改 `$http_host;`（保留端口），重建 frontend。
**验证**：带端口 Origin 登录 200 / 跨站 Origin 403 / 无 Origin 200。
**教训**：nginx 反代 Host 一律用 `$http_host`，`$host` 会剥端口破坏依赖 Host 的校验。

### 16. .env 新增变量容器内不生效
**症状**：往 `.env` 加 `ADMIN_USERNAME` 后重启 backend，`docker exec ... env | grep ADMIN` 为空。
**根因**：compose 的 backend.environment 用 `${VAR}` 显式展开，**没有 `env_file: .env`**——.env 只作为 compose 变量来源，未在 environment 列表里的变量不会注入容器。
**解决**：新增环境变量必须**同步改 docker-compose.yml**（在 backend.environment 加一行 `${VAR}`）再 `docker compose up -d --force-recreate backend`。
**验证**：`docker exec gongkao-backend env | grep '^ADMIN_'` 可见三值。

### 17. /admin.html 与主站是同一个页面
**症状**：访问 `/admin.html`、`/dashboard.html` 都渲染主站 index.html。
**根因**：frontend 镜像是**旧构建**——容器 html 目录只有旧版单体 index.html，没有 admin.html/dashboard.html/js/ 目录；nginx `try_files $uri $uri/ /index.html` 兜底导致一切路径显示主页。
**解决**：更新本地 Dockerfile（COPY js/ + dashboard.html），全量上传前端 13 文件，重建 frontend。
**教训**：前端改动后必须 build frontend；验收多页面时先确认容器内文件清单。

### 18. admin 创建老师 500（KeyError: temperature）
**症状**：后台「新增老师」只填必填三项，保存报 500；日志 `KeyError: 'temperature'`。
**根因**：`_validate_teacher_payload` 只校验**传入**字段，未传的 temperature/top_n/threshold 不进输出 dict；`create_teacher` 的 INSERT 直取 dict → KeyError。
**解决**（已修）：`create_teacher` 里 `setdefault("temperature",0.3)/setdefault("top_n",6)/setdefault("threshold",0.5)`。
**教训**：create 语义接口必须补齐默认值，与 DB 表 DEFAULT 一致；测试要覆盖「最小字段创建」路径。

### 19. FastAPI 路由遮蔽（静态路由被动态路由吞掉）
**症状**：`GET /api/orders/user` 返回 404「订单不存在: user」。
**根因**：`/orders/{order_id}` 先注册，`/orders/user` 被当作 `order_id="user"` 匹配。
**解决**：静态路径（`/orders/user`）注册到动态路径（`/orders/{order_id}`）**之前**；或改名避开冲突。
**教训**：FastAPI 按注册顺序匹配，静态路由必须优先；用 `curl` 冒烟覆盖所有静态子路径。

### 20. CLI ingest 后常驻 API 问答 500（Chroma Nothing found on disk）
**症状**：用 `docker exec ... python -m poc.cli ingest` 入库（375 块成功、collection_count/documents 都正常），但 HTTP `POST /api/ask?teacher_id=T003` 返回 500 `Error creating hnsw segment reader: Nothing found on disk`。
**根因**：chromadb 1.5.9 的常驻 uvicorn 进程持有 Chroma 客户端，外部 CLI 进程（独立 python 进程）写入的新 collection 索引，常驻进程查询时加载不到磁盘段（进程间客户端状态不同步）。容器内另起 python 直接查询却正常——证明磁盘索引没坏，是常驻进程状态旧。
**解决**（已修）：`docker compose restart backend`（Chroma 客户端重新初始化即恢复），T001 无回归。
**教训**：**任何 CLI/脚本方式 ingest 入库后，必须重启 backend 容器**（或改走 API 上传让常驻进程自己写）。本地开发无此问题因为每次都是新进程。
