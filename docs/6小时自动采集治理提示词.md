# 6小时自动采集深水区治理 · 工作提示词

> 版本：v1 · 2026-09-13
> 用法：将本文整份粘贴给具备终端/SSH/浏览器能力的 agent 执行。
> 背景：自动采集功能域 42 项逐项真实检测已全部 PASS，本轮转入**运行质量治理**。
> 时间：6 小时，按 Asia/Shanghai 计算。

---

## 0. 环境与基线（前 15 分钟，必做）

- 仓库 `D:\xiangmu\gongkao`；线上 `http://YOUR_SERVER_IP:3000`（nginx → backend:9000）
- SSH `ubuntu@YOUR_SERVER_IP`（凭据见 `scripts/_detect_ssh.py`，**本轮结束前删除该脚本及全部 `_detect_*.py` 临时文件**）
- 管理员 token：`scripts/_detect_api.py` 内 get_token
- 先备份 `GET /admin/autocollect/config` 与 `GET /admin/autocollect/llm/channels` 完整 JSON 到本地，收尾时逐字段复核
- 先确认：守护是否在跑（`GET /admin/autocollect/status`）、失败集规模、当前 LLM 用量

## 1. 第一优先级（0.5h~1.5h）：LLM 通道超时治理

**现状**：失败集 errors_detail 大量 `调用超时(60s/120s)`，`vsllm.cc`（glm-4.7-flash-free 等）与 `ai.anyyds.cn` 通道 avg_ms 达 84s+、fail 42 次，拖慢采集并触发退避。

任务：
1. `POST /admin/autocollect/llm/channels/test` 全通道并发测速，按延迟排序输出（需留存结果）
2. 对 avg_ms>30s 或 fail_count 高且近 24h 无成功的通道，评估是否在 `llm_channels` 中降权/停用；**操作前先 PUT 备份**，操作后 GET 复核
3. 若为网关侧问题：确认 `_healthy_order_channels` 能否把高失败通道排后（容器内 `python -c` 直调验证）
4. 调整 `fail_alert_threshold` 通知阈值，使通道连续失败能触发告警（若未配置 webhook 则仅记录）

**验收**：通道测试有逐通道延迟表；本轮操作均有备份+复核；`_healthy_order_channels` 排序符合"低延迟/低失败优先"。

## 2. 第二优先级（1.5h~3h）：存量伪题审计与清理

**现状**：历史话题确认题库曾混入 SEO 伪题（如"XX笔试时间是什么时候？27考生必看"），已知 ID 段 2258/2261/2269/2273/2274/2277 等；门控关键词已补（培训/辅导/上岸/机构），但存量需人工复核。

任务：
1. 用 `_gongkao_real_question_shape`（容器内直调）对全部 `source` 为采集来源的题目做**批量离线扫描**，输出疑似伪题清单（含拒因）
2. 人工逐条复核清单（抽样 20%），确认拒因合理
3. 确认伪题：`DELETE /admin/questions/{qid}` 前先插入 `question_bank_deleted_backup` 备份（复用既有备份机制），删除后复核 `GET /admin/questions/stats` 总数回落
4. 将本次命中但门控未拦截的新形态，追加为 `_gongkao_real_question_shape` 或关键词门控的回归样本（写入 `test_autocollect_offtopic.py`）

**验收**：产出伪题清单（qid+拒因+处置）；删除数=备份数；回归测试新增样本通过。

## 3. 第三优先级（3h~4h）：真实采集轮次验证

任务：
1. 清理失败集中的死源：对 `整站爬取未获得有效页面`（aipta.com/gkzhenti.cn 根域 13 连败）确认站点是否已失效，失效则从 `urls` 移除（先备份）
2. 触发一轮真实 /run（收紧 max_per_cycle=20 + llm_budget_chars=200000，跑完恢复）：
   - 观察漏斗 `search→site→detail→qualify→parse→added` 各环节数量
   - 确认新增题目无伪题（抽查当轮 5 题喂 `_gongkao_real_question_shape`）
3. 验证 `retry_failed_auto` 与退避窗口（对比失败集 ts 与当前时间）

**验收**：漏斗各环节有真实数字；新增题目抽查全过正象校验；配置恢复 baseline。

## 4. 第四优先级（4h~5h）：回归与部署

任务：
1. 本地 `python tests/test_doc_import_path.py` 与 `python tests/run_tests.py`——允许唯一失败 `test_learning_report.py`（既有 C4 复习调度问题）
2. 如有代码改动：走 `scripts/deploy.py` 部署（先 py_compile 预检 → build → up -d → 健康检查），静态资源改 `?v=20260913x` 递增
3. 部署后浏览器过一遍采集管理页（总览/类型/通道/内容/日志五子页，无 console 错误）

## 5. 收尾（5h~5.5h）：清理与复核

1. 删除全部 `scripts/_detect_*.py`（含 SSH 凭据）与 `scripts/_shot_*.png`
2. config/channels 逐字段比对备份；`_检测_` 前缀文档/文件确保零残留
3. webhook 监听进程确认已停

## 6. 复盘（5.5h~6h）：输出报告

- 矩阵：`任务 | 动作 | 证据（真实返回值/截图/文件状态） | PASS/FAIL/BLOCKED`
- 根因分析（通道超时的处置结论、伪题新形态特征）
- 成本统计（本轮 LLM 调用量/预算占比）
- 恢复确认清单与总体结论（可发布/需修复清单）

---

## 硬性纪律

1. 所有配置改动：先备份→操作→GET 复核，全程最多触发 2 次真实 /run（且都收紧预算）
2. 删除题目必须入 `question_bank_deleted_backup`，禁止裸 DELETE
3. 数据零污染：测试文档一律 `_检测_` 前缀，测完真删
4. 结论三态 PASS/FAIL/BLOCKED，FAIL 附根因线索，禁止"读代码认为正确"
5. 6 小时到点必须停在收尾阶段并输出完整报告，未完成项列为待办清单
