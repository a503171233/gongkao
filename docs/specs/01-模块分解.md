# 01 · 模块分解与边界（18 模块全景）

> 版本：v1.0 · 依据 `00-总设计.md`
> 用途：给「分派独立开发 + 统筹验收」用的模块清单与依赖关系图。

---

## 1. 模块编号规则

```
A 系列 = 网站一（前端业务站点），5 个模块
B 系列 = 网站二（RAG 内核服务站点），8 个模块
C 系列 = 扩展业务域（可运营化），5 个模块
```

每个模块说明书文件名：`modules/A1-用户管理模块.md` 等。每个模块有独立开发目标、接口契约、依赖项、验收标准，可交付给任一 AI 独立实现。

## 4. 独立开发准则（统筹约束）

1. **只动自己模块的文件**：A 系列只能改 `frontend/` 对应区块；B 系列只能改 `backend/poc/` 对应模块文件与 `api.py` 中对应路由。跨模块文件（`api.py`/`index.html`/`config.py`）由统筹或 B1 模块负责，其他模块不得整体重写。
2. **契约优先**：所有模块以 `02-数据契约.md` 为准。改契约必须先提变更，统筹统一更新 `02`，再通知相关模块。
3. **可独立验证**：每个模块交付时必须附「自测方式」（单元测试 / CLI / 接口 curl 示例），不能依赖其他模块未完成的代码。
4. **禁止引入新重依赖**：不得擅自加框架（如前端引 Vue/React、后端引 ORM），如需新增依赖必须先向统筹申请。
5. **遵循既定坑位**：开发时必读 `docs/项目状态总览.md §五/§六` 与对应模块说明书的「坑与注意事项」。

---

## 5. 开发顺序建议（给统筹排期）

**批次 1（内核，无新依赖，风险低）**：B5 → B6 → B7 → B8 → B3 → B2 → B4 → B1
**批次 2（前端，依赖 B1 契约）**：A1 → A4 → A2 → A5 → A3
**批次 3（扩展域，依赖 B/A 稳定）**：C1 → C2 → C3 → C4 → C5

> 说明：B 系列多为「对现状的清晰拆分 + 补齐缺失」（如 B7 重试降级），可先于前端重构并行推进。
